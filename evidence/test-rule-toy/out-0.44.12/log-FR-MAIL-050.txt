**Gaps for the spec author**
1. **A store or the secret fails, or hangs:** should the client get NO or have the connection closed, should there be a timeout, and does the attempt count toward the limit? The toy saw the connection close when the store was down and a login that never answered when it hung.
2. **The limiter itself fails:** two parts of the requirement conflict. Letting logins through breaks the limit, and refusing them refuses the mail app that reconnects often.
3. **A counter that never counts:** the contract suite would pass it, because 0 equals 0. Should the suite require that a correct password shows some work?
4. **"Never chosen":** how is it enforced? One option is a package that only generates passwords and their entries. Either way, how strong must a generated password be?

**The check I was least sure belongs:** the unit check on the license and imports. That part is a requirement in the statement, so something must check it. But it reads like a repo rule for CI, and it is not a rule of logic, which is what a unit check is supposed to be. I kept it because no other check fails when it breaks.

A close second is putting the 502-byte user case into the contract suite scenario. That failure was seen in the key-value store strategy, not in the basic login, but the toy asked for a suite clause covering it.
